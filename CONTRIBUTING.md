# Contributing to Rehearse

Thanks for taking the time to contribute. This guide covers the
**two published packages** in this repo, both Apache 2.0:

- [`@rehearse/cli`](cli) — local-first GitHub Actions runner and pipeline CLI (binary: `rh`)
- [`@rehearse/ci`](ts-ci) — TypeScript pipeline SDK that compiles to GitHub Actions YAML

`git-engine/` (`@rehearse/git-core`) is internal and frozen — it is not published or tested in CI.

There is no closed-source product. Everything in this repo ships under
Apache 2.0 to npm; the marketing site (`site/`) is private but contains
nothing proprietary.

## Development setup

```bash
# Requires Node 22+ and pnpm 9+
pnpm install
pnpm turbo build
pnpm turbo typecheck
pnpm turbo test
```

To work on a single package:

```bash
pnpm --filter @rehearse/cli test
pnpm --filter @rehearse/ci test
pnpm --filter @rehearse/cli dev -- ci compile   # run the rh CLI from source
```

To run the runner against a workflow during development:

```bash
node cli/dist/index.js run .github/workflows/ci.yml
```

To run the cross-OS bench against `act`:

```bash
pnpm tsx bench/compare.ts --skip-cold
```

## Project layout

```
cli/           @rehearse/cli — the runner and the rh CLI
ts-ci/         @rehearse/ci — TypeScript → GitHub Actions YAML SDK
git-engine/    @rehearse/git-core — pure-TS git engine (internal, frozen)

site/          marketing site at rehearse.sh (private, deploys as Workers Static Assets)
bench/         cross-OS benchmark harness (runner vs act vs GitHub-hosted)
poc/           bench fixtures + a hono clone in poc/playground (gitignored)
scripts/       release.mjs (retired stub — releases are automated, see Releasing)
.rehearse/      our own CI pipelines authored in TypeScript
.github/       workflows generated by `rh ci compile` from .rehearse/pipelines/
```

## What we look for in a PR

1. **Tests.** Every public-API change has a matching test.
   - `@rehearse/cli` tests live in `cli/test/` (`pnpm --filter @rehearse/cli test`).
   - `@rehearse/ci` has compiler snapshot tests under
     `ts-ci/test/compiler/snapshots/`. If your change updates YAML output,
     delete the affected snapshot and re-run `pnpm --filter @rehearse/ci
     test` to regenerate; commit both.
2. **Typecheck clean.** `pnpm turbo typecheck` must pass.
3. **No new runtime deps in `@rehearse/ci`.** The compiled YAML must work
   without Rehearse at runtime — that means the SDK itself can't drag in
   anything beyond what's in the runtime contract. Dev-only deps are fine.
4. **No regressions in the runner's compat or bench numbers.** If you're
   touching the runner core, run
   `node cli/dist/index.js compat poc/playground/hono/.github/workflows/ci.yml`
   and `pnpm tsx bench/compare.ts --skip-cold` — both should be roughly
   stable. `bench/RESULTS.md` is the source of truth for the marketing
   site's claims.
5. **Conventional commits.** See below — releases are generated from them.

## Conventional commits

Commit messages are the release notes, so the format is enforced:
`type(scope): subject`, using the standard
[`@commitlint/config-conventional`](https://github.com/conventional-changelog/commitlint/tree/master/%40commitlint/config-conventional)
types: `feat`, `fix`, `perf`, `revert`, `docs`, `test`, `refactor`, `style`,
`build`, `ci`, `chore`.

- **Scope** is optional and names the package or area: `cli`, `ci`, `site`,
  `bench`, `compat`, `deps` (runtime dependency bumps), `deps-dev`
  (devDependency bumps). Old ad-hoc types like `compat:`, `site:`, `bench:`,
  `deps:` and `release:` are no longer valid — use `test(compat):`,
  `docs(site):`, `chore(bench):`, `fix(deps):` and so on.
- **What releases:** `feat` → minor, `fix` / `perf` / `revert` → patch, and a
  `!` (`feat!:`) or `BREAKING CHANGE:` footer → minor while we are on 0.x.
  `docs`, `test`, `chore`, `ci` and friends never cut a release, and neither
  does a commit that only touches `site/`, `bench/`, `poc/`, `demos/`,
  `examples/`, `packages/`, `rehearse-pro/`, `git-engine/` or `.rehearse/`.
- **Pre-push hook.** `pnpm install` points `core.hooksPath` at the tracked
  `.githooks/`. On `git push` the hook lints every commit being pushed
  (including direct pushes to `main`), then runs `.git/hooks/pre-push` if you
  have one (e.g. from `rh install-hook`). WIP and fixup commits are fine
  locally — they are only checked on push. `git push --no-verify` skips it.
- **The PR title is what lands.** PRs are squash-merged using the PR title and
  body, so the `pr-title` check lints the title and the body becomes the
  commit body (put `BREAKING CHANGE:` / `Release-As:` footers there).

## Releasing

Releases are automated with [release-please](https://github.com/googleapis/release-please).
Don't tag by hand and don't run `pnpm release` — it is retired and exits 1.

1. Every push to `main` updates a standing release PR titled
   `chore(main): release X.Y.Z`. It bumps `@rehearse/cli` and `@rehearse/ci`
   in lockstep and writes the `CHANGELOG.md` entry from the conventional
   commits since the last release.
2. Merge that PR to release. release-please tags `vX.Y.Z` and creates the
   GitHub Release, and the `publish` job in the same
   [`release.yml`](.github/workflows/release.yml) run publishes both packages to
   npm under `latest`. If publishing fails, fix the cause (usually npm auth)
   and use **Re-run failed jobs** on that run.
3. To force a version, add a `Release-As: x.y.z` footer to a commit (for a
   squash-merged PR, put it in the PR body).

Runtime dependency bumps from Dependabot arrive as `fix(deps):` and cut a patch
release; `chore(deps-dev):` and `ci(deps):` bumps don't. There is no prerelease
channel. Config lives in `release-please-config.json` and
`.release-please-manifest.json`.

## Reporting issues

- **Bug reports** — minimal repro plus your Node / pnpm / OS versions and
  the workflow YAML you ran.
- **Compat regressions** — if `rh compat <yourworkflow>` reports a
  step as `uses-unsupported` and you think it should be supported, please
  open an issue with the action ref and version.
- **Bench regressions** — if a bench number drifts noticeably from
  `bench/RESULTS.md`, mention the OS, the warm-cache state, and how you
  reproduced.
- **Security** — please email <george@flarefound.com> rather than opening
  a public issue.
